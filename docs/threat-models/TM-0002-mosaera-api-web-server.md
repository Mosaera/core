# Threat Model: Mosaera API / web server (TM-0002)

Status: active
Date: 2026-07-11 · Last updated: 2026-07 (rate-limiting ADR-0050 + login-backoff ADR-0051 controls added; both shipped)
Owners: Alejandro Rengifo
Related ADRs: ADR-0004 (auth), ADR-0005 (config-in-UI), ADR-0006 (transcript)

## Scope

The FastAPI application (`apps/api/mosaera_api/`, assembled by `create_app`) and
the built SPA it serves from the same origin: the auth bootstrap + login surface
(`routes/auth.py`), the authenticated `/api/*` run/history/backlog/project
surface, the admin-gated config/secret surface (`routes/settings.py`), the run
transcript + SSE endpoints (`routes/runs.py`), the bind/auth guards and
middleware in `app.py`, and the session/credential primitives in `auth.py`.

**Out of scope (covered by TM-0001):** the CLI-driven PM → Coder → Reviewer
agent loop, the Docker/subprocess sandbox, repo tools, and dependency install.
This TM treats the agent loop as a downstream trusted-by-the-API subsystem; it
models the **network/web attack surface** that TM-0001 does not — the HTTP server
that now fronts that engine and holds its credentials.

## Assets

- **User password hashes** — `hashlib.scrypt` (N=2¹⁴, r=8, p=1, 16-byte salt),
  encoded `scrypt$N$r$p$salt$hash`, stored in the users table (`auth.py`).
- **Session tokens** — a 32-byte `secrets.token_urlsafe` bearer rides an HttpOnly
  cookie; only its **SHA-256** is stored (`hash_token`), so a DB leak cannot be
  replayed as a live session.
- **Provider API keys + GitLab PAT at rest** — written to `<home>/settings.json`
  (`0600`, gitignored) by `settings_store.write_settings`; masked on read
  (`mask_secret` → `…last4`), never returned raw.
- **The operational config** (`settings.json`) — budgets, iteration caps, the
  breaker, model routing, the delete-tool flag; a write is a change to how every
  subsequent run behaves and spends.
- **Run transcripts** — durable `run_events` (tool activities, agent reasoning,
  node completions, gate) served by `GET /runs/{id}/transcript`; may embed
  reasoning text and tool/file paths from a run.
- **Availability + spend** — the API launches sandboxed runs that cost tokens/$
  and hold a Docker socket-adjacent execution path (TM-0001).

## Actors

- **Anonymous** — an unauthenticated caller that can reach the bind. On a
  configured instance it may touch only the open bootstrap paths.
- **Member** (non-admin user) — a logged-in session; may run tasks and read
  history, but not manage users or write config (two-tier gate).
- **Admin user** — a logged-in session with `is_admin`; may write config/secrets
  and manage the (capped) user set.
- **Service-token holder** (`MOSAERA_API_TOKEN`) — a machine/SSE client; gets
  full `/api/*` **run/read** access but is **not** admin (config writes refuse).
- **Admin-token holder** (`MOSAERA_ADMIN_TOKEN`, `X-Mosaera-Admin`) — the
  proxy-agnostic capability to reconfigure the server / write a credential when
  there is no logged-in admin session.
- **Network attacker** — on-path or same-LAN; may attempt bind exposure,
  token/cookie theft, CSRF, brute force, or replay.

## Architecture and trust boundaries

1. **Loopback vs public bind** (`guard_bind`, enforced in *both* `main()` and
   `create_app`). Loopback (`127.0.0.1`/`::1`/`localhost`, the default) is
   permitted with no auth. A non-loopback bind is **refused at startup** unless
   `MOSAERA_API_TOKEN` is set AND the sandbox is Docker (the subprocess backend
   runs test code on the host, so it must never be reachable off-box). `""` is
   explicitly *not* loopback (uvicorn binds all interfaces).
2. **Unauthenticated vs authenticated** (`_authenticate` middleware). Every
   `/api/*` request (except `OPTIONS` and the three open bootstrap paths) must
   present **either** a valid session cookie **or** the service token
   (constant-time, `Authorization: Bearer` or `?token=`). Enforcement turns on
   only when auth is *configured* — a token is set OR user accounts exist — so an
   unconfigured loopback dev box stays open.
3. **Member vs admin** (`_require_admin_ctx`). A logged-in admin passes; a
   logged-in member is refused (403); with no session it falls back to the
   service tiers (`_require_admin`: admin token if set, else refuse on a
   token-protected instance, else the loopback same-host gate for plain dev).
   This is the config/secret trust boundary.
4. **Server vs SPA.** The built bundle is served from the same origin (top-level
   paths route to `index.html`; `/api/*` wins). Same-origin keeps the session
   cookie usable without CORS credentials; CORS `allow_origins` defaults to the
   Vite dev origin only.

## Entry points

- `GET /api/auth/status`, `POST /api/auth/login` — the **only** middleware-exempt `/api` paths
  (SPA bootstrap: probe state / log in). **Neither creates anything.** `POST /auth/setup` was the
  third and was deleted 2026-08-26 (ADR-0116): the first administrator is created by
  `mosaera-setup`, in a terminal, against the database directly.
- The authenticated `/api/*` surface — runs, history, backlog, projects,
  messages, voice, GitLab introspection.
- `PUT /api/settings/general` (and `PUT /pricing`, `PUT /providers`,
  `PUT /cost-modes`, `POST /gitlab/config`, `POST /features/delete-tool`,
  `POST/DELETE /auth/users`) — **privileged config/secret/user writes**, admin-gated.
- `PUT /api/projects/{id}/charter` (#42/ADR-0047) — the **trusted operator-intent write**
  (goal/constraints/**posture**, a governance declaration), admin-gated like the config
  writes; the intake chat only *proposes* (`charter_proposal` in the reply — never a write
  path), and posture is enum-validated deny-by-default at the store.
- `GET /api/runs/{id}/transcript` + `GET /api/runs/{id}/events` (SSE) — run
  disclosure; SSE accepts `?token=` for header-less transports.
- `GET /{full_path}` — SPA static serving (path-confined to `dist/`).

## Threats

| Threat | Abuse case | Impact | Mitigation | Residual risk |
|---|---|---|---|---|
| Session token theft / replay | Attacker obtains the raw session cookie (network sniff on http, malware) and replays it | Full session hijack for its TTL | HttpOnly + `SameSite=Lax`; `Secure` opt-in (`MOSAERA_COOKIE_SECURE=1`) behind TLS; only SHA-256 stored (DB leak ≠ live session); 14-day TTL with server-side expiry + prune | Medium — a stolen live cookie is replayable until logout/expiry; no rotation/binding; `Secure` is off by default on plain-http LAN deploys |
| Cookie theft via XSS | Injected script reads `document.cookie` | Session exfiltration | Session cookie is **HttpOnly** — unreadable from JS; the token never appears in the SPA's JS state | Low (for the cookie); a same-origin XSS can still *act* as the user via fetch |
| CSRF on state-changing POSTs | A third-party page auto-submits to `/api/runs`, `/api/settings/general`, etc. riding the ambient cookie | Unwanted run/config change | `SameSite=Lax` blocks cross-site cookie send on the relevant methods; same-origin SPA posture; JSON bodies + no simple-form endpoints; CORS not credentialed for foreign origins | Medium — no per-request CSRF token; `SameSite=Lax` (not Strict) still allows top-level cross-site GETs, and correctness relies on the browser honoring it |
| Session fixation | Attacker plants a known cookie pre-login | Post-login hijack | A **fresh** token is minted server-side on every setup/login (`_issue_session`) — the client cannot choose its session id; logout deletes the server session | Low |
| **Brute-force login (ADR-0051)** | Automated password guessing / credential-stuffing against a known username on `/auth/login`. ADR-0050's rate limiter cannot reach it: that route is middleware-exempt and *pre-credential*, so `subject_for` finds no credential and skips it — the only key left is the client IP, which behind the recommended reverse proxy is shared by every client (limiting on it would let one attacker lock out the team) and `X-Forwarded-For` is deliberately untrusted | Account takeover on weak passwords | **Per-ACCOUNT backoff** (`login_backoff`, Alembic `0016`): `threshold` attempts (default 5), then an escalating lock (30s doubling → 900s cap, `MOSAERA_LOGIN_BACKOFF_*`, env-only, default **ON**) → **429 + `Retry-After`**; a success clears the streak; an idle `reset` window starts it over. Durable and **exact across workers** (the rate limiter's in-process window is only per-worker). Check-and-claim is ONE conditional UPSERT and the slot is claimed **before** verification — counting failures *after* ~130ms of scrypt is a TOCTOU race that bounds sequential rounds, not guesses (ADR-0050 §5's race, at 130ms scale); a 40-thread test asserts exactly `threshold` of 40 racing callers win. A refused attempt claims nothing, so hammering can't extend a lock. Key = `sha256(username.strip())`, case-SENSITIVE and normalized once for both lookup and bucket (casefolding merges the distinct accounts `admin`/`Admin`, and since a success DELETES the bucket a member holding `Admin` could clear the admin's counter at will); hashed so the table can't capture passwords typed into the username box. Plus: scrypt per attempt, generic 401, 8-char minimum | Medium — bounds ONLINE guessing against one account. Does nothing for a stolen password, an offline attack on a leaked hash, or a distributed campaign across MANY usernames at a few attempts each (each subject stays under its own threshold) — those want credential-stuffing detection + password policy, not a counter. **New cost:** attacker-induced lockout (see the row below) |
| **Username-enumeration oracle via login timing (ADR-0051) — this threat model previously claimed it was mitigated** | `routes/auth.py` read `ok = creds is not None and verify_password(...)` under a comment asserting *"Constant-ish work whether or not the user exists"*. Python's `and` short-circuits, so an unknown username **never ran scrypt at all**. Measured **~129ms** (real account) vs **sub-ms** (fictional); end-to-end over HTTP, **194ms vs 9ms**. Not a statistical side-channel needing many samples — a **single-request** oracle readable with a stopwatch. The mitigation cell in this file asserted the property the code destroyed, which is plausibly why it survived: a threat model that reports a hole closed retires the fix from everyone's queue | Free enumeration of valid usernames → the precondition for the brute-force row above, and for targeted phishing | Verify against a dummy hash instead of short-circuiting: `verify_password(password, creds["password_hash"] if creds else _DUMMY_HASH)`. The dummy is random bytes in scrypt's stored shape, not a real hash — `verify_password` parses `scheme$n$r$p$salt$hash` and recomputes, never checking the digest is genuine scrypt, so it costs **identically** (measured 132.4ms vs 131.8ms, ratio 1.004) and can never match. **Unconditional** — unlike the backoff it is never capability-gated, because "no backoff" is a degraded control while "leaks existence" is a defect. Backoff is keyed on the SUBMITTED username so unknown accounts throttle identically: otherwise the 429 itself would be a cleaner, timing-free oracle. Regression tests drive the real endpoint (`test_an_unknown_username_costs_the_same_as_a_real_one` — it fails against the old code at 0.009s vs 0.194s; `test_the_429_arrives_at_the_same_point_for_real_and_fictional_accounts`) | Low — the dominant term (scrypt) is equalized; sub-ms differences (a row fetch vs none) remain and are not exploitable at this scale. **Latent:** bumping `_N/_R/_P` re-opens it INVERTED — existing users carry the old cheaper params in their stored hash while unknowns get the new dearer dummy, making unknown measurably slower. Unfixable in general (you can't know an unknown user's params); commented at `_N` — a bump needs rehash-on-login first |
| **Attacker-induced account lockout (ADR-0051, new)** | The deliberate cost of per-account backoff: anyone who can reach `/auth/login` and knows a username can hold that account locked by failing against it. Inherent to ANY per-account key — IP is unusable behind the proxy | Denial of sign-in for a targeted user. **This converts lost-admin unavailability from a host-access-only condition into a network-reachable, attacker-induced one** — a real change to the "last-admin lockout" row above | Bounded, not permanent: the lock is capped (`MOSAERA_LOGIN_BACKOFF_MAX_SECONDS`, default 900s) and a success clears the streak. `DELETE /auth/users/{id}/lockout` (admin-gated) clears a MEMBER's counter — it deletes a counter and can never mint a session, weaken a password, or bypass verification. **The operator escape hatch already exists and is the real answer: `MOSAERA_API_TOKEN`/`MOSAERA_ADMIN_TOKEN` reach `/api/*` WITHOUT `/auth/login`**, so an operator is never locked out of their own instance. `set_user_password` also clears the bucket, so an admin resetting a locked member's password doesn't hand them a password they still can't use | Medium — a determined attacker wins the post-window race and can keep one account out indefinitely. Accepted: throttling guessing REQUIRES refusing to check, and refusing to check is what a lockout is. Bounded blast radius (one account's sign-in), with a token path that bypasses it entirely |
| **Login CPU/RSS exhaustion (ADR-0051)** | `auth_login` is a sync `def`, so FastAPI runs it in anyio's ~40-thread pool — **shared with every other sync endpoint**. Each scrypt is ~130ms and ~16MiB (N=2^14, r=8), so a login flood saturates every core and ~670MB RSS and stalls the WHOLE API, not just login. ADR-0050's limiter does not meter this route | API-wide unavailability from one unauthenticated endpoint | A **non-blocking** `Semaphore` (`MOSAERA_LOGIN_VERIFY_SLOTS`, default 8) around verification → **503 + `Retry-After`** on contention. It refuses rather than queues — queueing would hold an anyio worker, which is the DoS itself and what "never block the interactive path" forbids. A flood now fails fast on one endpoint instead of melting the box. Per-account backoff additionally caps the cheapest variant (repeat one username → locked after `threshold`, then 429s with no scrypt) | Medium — the ceiling is **unchanged** by equalization (a known username always bought 130ms/req; equalization only removes the one-request recon step the oracle itself was providing). A rotating-username spray still costs `threshold × 130ms` per fresh username before that bucket locks. The semaphore bounds concurrency, not total work; a genuine fix wants an upstream/proxy limit |
| **Runaway or hostile authenticated client exhausts the API / model budget (ADR-0050)** | A retry loop, a stuck script, or an authorized-but-abusive caller hammers `/api/*` — or repeatedly `POST /api/runs` — with a **valid** credential. The API runs code and spends a model budget, so this saturates the interactive path for everyone and burns real money. Until now there was **no request metering of any kind** | Interactive-path starvation (the SPA/poll becomes unusable) + unbounded spend, from an ordinary client fault rather than an attack | Two controls, split by cost (ADR-0050). **Rate limit** — an in-process fixed window per *credential* (`MOSAERA_RATE_LIMIT_PER_MIN`, default **300/min**, `0` disables): one dict lookup, no DB, on every `/api` request. **Run quota** — a durable per-*account* daily cap (`MOSAERA_RUN_QUOTA_PER_DAY`, default **off**) enforced only on `POST /api/runs` via a single atomic conditional UPSERT (`run_quota_usage`, Alembic `0015`), so concurrent submits cannot admit `limit+1`; keyed on the real account so re-logging-in cannot reset it; admin-exempt (fair-share is between users; run budgets still bound them). Both answer **429 + `Retry-After`** (never 0). The limiter is registered **inside** the auth middleware, so only *authenticated* traffic is metered and junk credentials can never mint buckets (`test_limiter_runs_after_auth_so_a_401_wins_over_a_429`). **No loopback exemption** — the socket peer is meaningless behind a proxy (see the `_require_local_config` caveat), so the discriminator is the *credential*, not the peer; an exemption there would silently disable the control on every proxied deploy. Misconfiguration is **loud** (`SystemExit` on an unparseable/out-of-range value, and on a configured quota with no database to count in — ADR-0035). Tracking dict is bounded against credential rotation. `guard_bind`/session/token verification untouched | Medium — bounds **accident and unprivileged abuse**, which is the stated goal, but explicitly **not** an authorized-but-hostile caller: a service-token holder can present rotating cookies and land in fresh buckets (inherent to any limiter keyed on client-supplied identity; the answer to a hostile credential holder is revocation, not a counter). Also: **multi-worker deploys get per-worker rate limits** (`N × limit`; the quota is exact, being in Postgres) — solving it needs a shared counter store, a dependency this product declines; operators needing exactness set `limit / workers` or terminate at the proxy. Fixed windows allow a ~2x burst across adjacent windows. **#37 split the config surface:** the **quota** is now a `GENERAL_KNOBS` knob (`run_quota_per_day`), read live on `POST /api/runs` so an admin can set/disable it from Settings with no restart — via the existing admin config-write path, so no new external surface and the blast radius is unchanged (metering only refuses → availability, never access); the **rate limit stays env-only** (deployment infra, on every request, loud-parse — ADR-0050 §2/addendum), so the always-on control is still not UI-reachable |
| 5-seat-cap bypass | Create more than the allowed accounts to sprawl the admin surface | Governance sprawl | `create_user` enforces `max_users=5` atomically in the store; over-cap → 409 (`test_five_seat_cap`) | Low |
| Last-admin lockout / lost-admin recovery | Delete the only admin, or lose all admin credentials | Instance un-administrable | `delete_user` refuses when `count_admins() <= 1` (`test_cannot_remove_last_admin`); recovery path is operator-level (DB/env `MOSAERA_ADMIN_TOKEN`) | Low-medium — deletion is guarded, but a genuinely lost sole-admin password has no in-app reset; recovery needs host/DB access |
| Unconfigured-loopback-open posture | On a dev box with no token and no users, `/api/*` is fully open | Local unauthenticated use (by design) | Scoped to loopback (`guard_bind` blocks a public bind without a token); enforcement auto-engages the moment a token is set or the first user is created | Low — bounded to a same-host dev machine; a public bind can't reach this state |

| Privileged config mutation | Non-admin/anon calls `PUT /settings/general` to raise budgets, disable the breaker, enable the delete tool | Weakened run governance, spend blowout | Admin-gated (`_require_admin_ctx`): logged-in admin, else admin token, else refuse on a token-protected instance / loopback gate on dev; values coerced against the knob spec (`coerce_general_patch`); `test_member_cannot_manage_users_or_write_config` | Low-medium — a compromised admin session/token can legitimately do this; blast radius is spend/behavior, not host access |

| **Run/project id path traversal (ADR-0038)** | `run_id`/`project_id` from the URL is joined onto `workspaces_dir`/`projects_dir` as a trusted single segment; `%2e%2e` (proxies do NOT normalise it; uvicorn decodes it to `..` in the `[^/]+` path param) escapes the base dir. `DELETE /runs/%2e%2e` (`delete_run`) ran `rmtree(workspaces_dir / run_id)` with **no check at all**; `GET /runs/%2e%2e/files/settings.json` (`download_file`) built the containment root FROM the id *before* the `is_relative_to` check, so the check then passed for `.mosaera/settings.json`. Reachable by any session **OR the plain service token, which is not admin (ADR-0004) ⇒ privilege escalation** (a non-admin destroys/exfiltrates admin-only secrets) | Deny-by-default `_pathsafe`: `safe_segment` rejects a non-segment id at the boundary (clean `400`); `contained_path` resolves + proves-under-base at **every** id→path sink (`download_file`/`delete_run`/`open_mr`/`run_report`/`delete_project`, and — completing the parity in ADR-0042 — `project_file` plus `_project_ws` behind `project_files`/`project_patch`, which had still built their root from the raw `project_id`). The server-minted id charset (`run` `YYYYMMDD-HHMMSS-<6hex>`, `project` `proj-<slug>-<6hex>`) is a strict superset → no legitimate id is rejected. Unit + route regression tests drive the exact `..` request → `400` **and** assert the base tree survives (`test_pathsafe.py`, `test_*_rejects_traversal_id`) | Low — boundary + sink guards close both live exploits. `factory.py`'s run-creation join is server-minted (not attacker-supplied) and left un-wrapped. A first-pass audit had misfiled this class as Low ("each handler re-checks `is_relative_to`" — `delete_run` did not, and `download_file`'s check anchored on a poisoned root) |
| CORS misconfiguration | An operator widens `MOSAERA_API_CORS_ORIGINS` to `*` | Cross-origin API access | Defaults to the single Vite dev origin; credentials are cookie-based (same-origin) so a foreign origin can't ride the session without an explicit allow; CORS stays the outermost middleware and answers preflight | Low-medium — operator-controlled; a careless `*` plus a lax cookie would widen exposure |
| **MR-opening authority + token routing (ADR-0102)** | `push`/`open_pr` sat in `GATED_ACTIONS` with NO `request_approval` caller (an inert control), while `POST /runs/{id}/open-mr` fabricated a retroactive `open_pr` approval row and pushed with the **global** GitLab token even for project runs | A reader of the approval record believed a human approved a push no one was asked about; a project push rode a broader credential than the project's own `write_repository` token | The inert actions are removed from `GATED_ACTIONS` (the set is test-pinned); the **authenticated endpoint IS the human approval** (session/service auth, ADR-0004) or the explicit `auto_open_mr` opt-in (ADR-0019); no approval rows are fabricated — the `mr.opened`/`mr.failed` audit event with the actor is the record; project runs use the project-scoped token and fail closed (400) without one | Low-medium — the global token still serves ad-hoc (project-less) runs, which have no other credential home (documented residual); endpoint auth is the sole human control for MR opening, so a compromised session can open (never merge) an MR |

Three-way token-routing invariant: project-write / project-api / global-adhoc never cross | Medium-low — the broader scope is the accepted, operator-opted-in cost of REST metadata; held only for human-in-the-loop actions, so the frequency-weighted privilege stays minimal. ## Security controls

- **Authn:** scrypt password hashing (`auth.py`); server-minted session tokens
  stored SHA-256; HttpOnly + `SameSite=Lax` cookie with opt-in `Secure`; shared
  service token via constant-time `secrets.compare_digest` (header or query).
- **Authz:** two-tier gate — service/session token grants run/read;
  `_require_admin_ctx` gates config/secret/user writes to a logged-in admin, an
  admin token, or (dev only) the loopback same-host check; deny-by-default
  middleware once auth is configured.
- **Bind safety:** `guard_bind` refuses an unauthenticated / subprocess-sandbox
  public bind, enforced in both entrypoints.
- **Secrets:** `settings.json` written `0600`; write-only over the API; masked on
  read (`mask_secret`); allow-listed keys (`_ALLOWED_KEYS`) keep stray input out.
- **Integrity/availability:** last-admin guard; 5-seat cap; spend persisted at
  park (MR !134); knob coercion/validation on every config write; orphan-run
  finalization on startup.
- **Login protection (ADR-0051):** per-**account** failed-login backoff (`login_backoff`, Alembic
  `0016`, env-only `MOSAERA_LOGIN_BACKOFF_*`, default ON) → 429 + `Retry-After`; durable and exact
  across workers; check-and-claim is one atomic conditional UPSERT with the slot claimed **before**
  verification. Login timing is **equalized** against a dummy hash so an unknown username costs the
  same as a real one (unconditional — never capability-gated). A non-blocking semaphore
  (`MOSAERA_LOGIN_VERIFY_SLOTS`) bounds concurrent scrypt so a login flood can't stall the shared
  anyio threadpool. Admin-gated `DELETE /auth/users/{id}/lockout` clears a counter (grants nothing).
- **Rate limiting / quotas (ADR-0050):** a per-credential in-process request
  window (`MOSAERA_RATE_LIMIT_PER_MIN`, default 300/min) + a durable per-account
  daily run cap (`MOSAERA_RUN_QUOTA_PER_DAY`, default off, `run_quota_usage`,
  Alembic `0015`) → **429 + `Retry-After`**. Metering only, never authorization:
  it can refuse a request auth already accepted, never grant one — so a bug here
  costs availability (a wrong 429), never access. Registered *inside* the auth
  middleware; keyed on the **credential**, never the socket peer (no loopback
  exemption — see the ADR-0050 threat row). Env-only, and loud on
  misconfiguration.
- **Schema:** user/session/run_events tables are Alembic-managed (TM-0001 note),
  no hand-rolled DDL.

## Validation plan

- **Auth (`apps/api/tests/test_auth.py`):** password hash roundtrip + wrong-
  password reject; credential validation; first-run setup locks after the first
  account then login/logout; 5-seat cap (`test_five_seat_cap`); member cannot
  manage users or write config (`test_member_cannot_manage_users_or_write_config`);
  last-admin deletion refused (`test_cannot_remove_last_admin`); service token
  grants API but not admin (`test_service_token_grants_api_but_not_admin`).
- **Bind + gate (`apps/api/tests/test_api.py`):** token gate enforced when set /
  open when unset (`test_api_token_gate_enforced_when_set`, `test_api_open_when_no_token`);
  `guard_bind` refuses an unauthenticated public bind and `create_app` re-enforces
  it (`test_guard_bind_refuses_unauthenticated_public_bind`,
  `test_create_app_enforces_bind_guard`); config write localhost-gated
  (`test_gitlab_config_localhost_guard`); masked token never echoed
  (`test_gitlab_config_writes_masked_never_echoes_token`); project token never
  leaked raw (`test_project_detail_never_leaks_raw_token`).
- **General settings + budget:** general-settings coercion via the settings
  router; restart cost persistence (`test_parked_run_persists_cost_for_restart_recovery`,
  `test_parked_run_survives_restart_and_resumes`).
- **Manual/post-deploy:** verify `SameSite`/`Secure`/HttpOnly cookie attributes
  behind the real TLS terminator; confirm the reverse proxy strips `?token=` from
  access logs.
- **Known gaps (accepted / follow-up):** online password guessing is bounded by scrypt cost **plus
  per-account login backoff (ADR-0051)** and per-credential API rate limiting (ADR-0050) — the
  remaining gap is **no distributed credential-stuffing detection** across many usernames; **no CSRF
  token** (protection relies on `SameSite=Lax` + same-origin posture); **no transcript-side secret
  scrubber**; secrets are **plaintext at rest by default** under `0600`, **optionally
  envelope-encrypted** by setting `MOSAERA_SECRET_KEY` (Fernet, ADR-0039).
