# Architecture Decision Records

Durable rationale for Mosaera's significant design decisions. Each ADR is immutable once
accepted; a superseding decision gets a new ADR that references the old one. The **merge
requests** (GitLab) remain the source of truth for *what* changed; ADRs capture *why*.

> **Direction & end goal:** these ADRs record decisions for the *current* system (the
> software-engineering team). For the north star — the firm of hireable teams, project
> onboarding + map, and the Free/Business/Regulated posture model — see
> [`../architecture/north-star.md`](../architecture/north-star.md); for what is built vs. planned,
> see [`../roadmap.md`](../roadmap.md). The firm ([ADR-0045](ADR-0045-the-firm-teams-as-modules.md)),
> posture-governance ([ADR-0046](ADR-0046-posture-and-autonomy-governance.md)), and onboarding
> ([ADR-0047](ADR-0047-project-onboarding-and-the-durable-map.md)) ADRs are the binding *decisions*
> for Waves B/C — the `Status` column below and the roadmap carry their live build state, not this
> intro.

**When to write an ADR** *(the canonical threshold)*. An ADR is required for a **durable decision** —
a change to an architecture/dependency boundary, a trust boundary or authority, a public/API/schema/
artifact contract, a cross-cutting operational model, or a hard-to-reverse/strategic direction.
**Not** for ordinary bug fixes, bounded implementation details, benchmark snapshots, or
red-team/experiment logs — those live in issues/MRs, the changelog, `../threat-models/` (any
threat-surface change), or `../engineering-history/`. See `AGENTS.md`.
